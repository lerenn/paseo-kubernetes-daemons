Getting started

Deploy the operator once, then request workspace environments from your main Paseo daemon.

Requirements

  • Kubernetes 1.32+ with dynamic PVC provisioning.
  • Paseo 0.15.3+ on your main daemon and workspace daemons.
  • Your main daemon can resolve and reach cluster Service addresses. Running it in the cluster is the simplest setup.
  • kubectl on the main daemon, with access to the managed namespace.
  • Docker for image builds; Node 22+ for plugin development.

Build your images

Clone the repository. Replace your-registry with a registry your cluster can pull from.

git clone https://github.com/lerenn/paseo-kubernetes-workspaces.git
cd paseo-kubernetes-workspaces

docker build -t your-registry/paseo-workspaces-operator:0.2.0 .
docker build -t your-registry/paseo-workspace:0.2.0 images/workspace
docker push your-registry/paseo-workspaces-operator:0.2.0
docker push your-registry/paseo-workspace:0.2.0

The workspace image contains Paseo, Codex and the bootstrap helper. Install your agent provider executables in a derived image and inject their credentials through a Kubernetes Secret.

Deploy the operator

Set the operator image in config/operator.yaml to the image you just pushed, then apply the manifests.

kubectl apply -f config/crd.yaml
kubectl apply -f config/operator.yaml
# Optional: cap aggregate workspace resources.
kubectl apply -f config/quota.yaml

Install the companion

Apply config/plugin-rbac.yaml and bind its Role to the main daemon’s ServiceAccount. The main daemon needs kubectl, namespace access, and permission to create credential Secrets and ConfigMaps.

cd plugin
npm ci
npm run typecheck
paseo plugin install "$PWD"

Set up from Paseo

  1. Open Kubernetes Workspaces from the top-left sidebar menu.
  2. Save your Kubernetes context, namespace and bootstrap-enabled workspace image. Check the connection; the panel shows operator installation guidance if needed.
  3. On the Providers tab, click Find providers to discover provider credentials and Codex MCP definitions on the main host. Select a Codex subscription login or provider API keys, plus the MCPs to reuse, then Save selection and Sync providers. Values stay out of the panel and workspace custom resource.
  4. On the Projects tab, add a repository by URL or local checkout, approve it once for new pods and click Sync project. The Overview tab tracks cluster, providers and projects.
  5. Create an environment. Bootstrap prepares writable Codex credentials, checks out the approved repository and configures project trust before the daemon starts.
  6. Once online, choose Open workspace to work on that daemon.

Ephemeral storage is enabled by default. Turn it off for a PVC. The new workspace image includes Codex and the bootstrap helper; use a fresh image tag when upgrading from the initial implementation.

Credential snapshots are not a live authentication broker. Re-sync after main-host credentials change. OS-keychain credentials and coordinated OAuth refresh across pods are not supported. MCP OAuth file-cache export is a separate explicit opt-in.

See the full bootstrap and credential guide for upgrade steps, RBAC bindings and supported credential sources.

Release deletes workspace storage. Export results first. For persistent volumes, physical deletion follows the StorageClass reclaim policy.

Check an environment

kubectl -n paseo-workspaces get pw
kubectl -n paseo-workspaces describe pod pw-demo
kubectl -n paseo-workspaces logs pw-demo

A Ready pod is not necessarily a connected host. Check the companion’s hostStatus and error fields for registration problems. Configure daemon authentication and network policy for your cluster; an optional policy is provided in config/network-policy.yaml.

See the reference for all configuration options.
